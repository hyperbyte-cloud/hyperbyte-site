The database

HyperbyteDB, on GitHub.

A time-series database that speaks InfluxDB v1. Same line protocol, same InfluxQL, written so tag cardinality is capacity rather than a ceiling. Cloud runs this binary. It does not fork it.

  • +Same /write and /query endpoints.
  • +Continuous queries and master-master replication in the open-source binary.
  • +Image: ghcr.io/hyperbyte-cloud/hyperbytedb, port 8086.
  • +Scale-out is linear. Add a shard, add the capacity. On Cloud, a shard is 4 CPU and 16GB.

Kubernetes

Swap the operator. Keep the URLs.

The HyperbyteDB operator installs with Helm or a single manifest. It registers HyperbytedbCluster, HyperbytedbBackup, and HyperbytedbRestore. Clients stay on port 8086.

Master-master replication is in the open-source binary, so high availability is not a licensing conversation. The operator write-up covers the CRDs, the proxy, and the cutover.

  • +Kubernetes 1.26+ and Helm 3.8+, or one YAML manifest.
  • +Same Telegraf and Grafana configs. Change the Service, not the clients.
  • +Backups and restores are CRDs. S3-compatible storage is for backup, not the write path.
# Helm, from GHCR
helm install hyperbytedb-operator \
  oci://ghcr.io/hyperbyte-cloud/charts/hyperbytedb-operator \
  --namespace hyperbytedb-operator-system \
  --create-namespace

# or one manifest
kubectl apply -f \
  https://raw.githubusercontent.com/hyperbyte-cloud/hyperbytedb-operator/main/dist/install.yaml

Benchmarks

Run the numbers yourself.

The capacity-plan figure is 1.5 million points a second sustained, p95 under 250ms. Scale-out is linear in the number of shards. The engine alone does about 99 million rows a second. Both ingest figures are published, and both can be re-run.
